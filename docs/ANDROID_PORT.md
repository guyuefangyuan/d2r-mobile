# Android branch: what this repository adds on top of upstream

[中文版 / Chinese](ANDROID_PORT.zh-CN.md)

Upstream [dodola/d2r-mobile](https://github.com/dodola/d2r-mobile) is an iOS / macOS project with
an experimental Android branch. This document records what the Android work here adds at the
framework level, why it is done that way, and what is still broken.

> Framework behaviour only — no game content. Test plan: [TESTING.md](../TESTING.md).
> Scope and copyright: [NOTICE.md](../NOTICE.md).

## 1. The touch-UI overlay has to travel inside the APK

The game's own UI layouts (the `layouts/xtouch_lay` and two sibling directories) only become the
touch variant through a rewritten data package. That "touch-UI overlay" is validated by
`dm_android_custom_overlay()` / `overlay_complete()` and must be exactly four files
(`ctrl_touch`, `touch_strings.tsv`, `data/.build.config`, `data/00-00000007.data`). It only takes
effect once `GameActivity.installOverlay()` copies it from the APK's `assets/overlay/` to
`files/d2r-mobile/romfs-overlay`.

Two traps, both fixed:

1. **The packager omitted the overlay.** Without `assets/overlay-manifest.json`,
   `installOverlay()` returned silently, the host logged `ANDROID_CUSTOM_OVERLAY
   base_unavailable=1` and ran the **stock Switch gamepad UI**: the character panel moved to the
   other side and the tappable "create new character" became a ✚ key prompt, so that device
   **could not create a character**. The overlay is now written into the APK archive directly
   (not through `aapt2 -A`, because aapt2 skips dot-files such as `data/.build.config`).
2. **Failures were undiagnosable.** `overlay_complete()` now reports
   `missing=<file> reason=<why> errno=<code>` per file, and `installOverlay()` logs
   `D2ROverlay: files=<n> rewritten=<n>`, with a warning when the manifest is absent.

## 2. Overlay controls scale with the picture, not with absolute dp

The on-screen controls (D-pad, confirm, back, start, mode, system, FPS) used fixed dp sizes. The
16:9 picture is about 1280 dp wide on a 10-inch tablet but only 617 dp on a 6.3-inch phone, so the
same absolute size is twice as large relative to the picture there — and "back"/"confirm" ended up
covering the game's own buttons.

```java
int[] picture = GameDisplayMetrics.fitGame(metrics.widthPixels, metrics.heightPixels);
overlayScale = Math.max(0.62f, Math.min(1f, picture[0] / metrics.density / 1280f));
```

- tablet: `3200 / 2.5 / 1280 = 1.0` → **completely unchanged**;
- phone: `2161 / 3.5 / 1280 = 0.48` → raised to the 0.62 floor (below that the touch target drops
  under 8 mm).

`overlayPx()` is `dp() × overlayScale`, and text sizes are multiplied by the same factor.
Full-screen loading text still uses plain `dp()`.

## 3. Do not let the Mali driver's error report take the session down

On the phone (Mali system driver), loading all class models in one upload burst produces
`mali: Received a GROUP_ERROR_FATAL error on group(0)` in `logcat`. We then read the occlusion
queries:

```
[nvn-vulkan] STOP vkGetQueryPoolResults(G.device, sub->occlusion, ...) (1)
#01 die()  #02 commit_after_gpu()
```

That path used to go through `CHECK()` → `die()` → `abort()`, which killed the whole session. It
now goes through `query_read_tolerant()`: when the driver cannot deliver a result, that frame's
sample count is treated as zero and a `QUERY_READ_FAILED` line is logged; picture and flow
continue.

> This is **resilience, not a fix**: the Mali error itself is still there and heavy load can still
> drop frames or produce an occasional bad frame.

## 4. Frame-rate tiers and cadence

- The system menu offers 30 / 40 / 60, stored in `files/d2r-mobile/diagnostics/present-hz.txt`
  (`RenderFpsStore`, AtomicFile plus read-back verification).
- Only integer division of the panel rate is available (120 Hz → 120/60/40/30); see
  `dm_android_present_power_period_ns()` in `dm/android/nvn_present_policy.h`, whose semantics are
  **cap only, never raise**.
- The internal 3D resolution has a separate dynamic profile (`ANDROID_3D_SCALE`, default 0.75,
  floor 0.6), orthogonal to the frame-rate tier.

## 5. Bitmap pools and uploads

- The pool "used" marking is set word-at-a-time (`pool_use_mark()`), and the range test is
  word-at-a-time too (`bitmap_any()`); measured `usemark_ms` 274 → 33.8 (−88 %).
- Pool page granularity is adjustable at runtime (`DM_SLOT_PAGE_SHIFT` 6..16, marker file
  `diagnostics/slot-page-shift.txt`).
- On suspend the pool mirror is released
  (`dm_vk_memory_trim_caches(DM_VK_TRIM_ALL|DM_VK_TRIM_POOLS)`), so the background process is not
  killed by `lowmemorykiller` and the game does not reload when you come back.

## 6. HUD assets

Skill rings, orb glyphs and joystick art come from `assets/d2r_hud/`, generated by
`dm/android/tools/stage_hud_assets.py` from your own copy of the game. Without it every skill ring
is black. **This repository does not ship those assets.**

## 7. Diagnostic markers

Create an empty file under `files/d2r-mobile/diagnostics/` to enable the matching log:

| Marker | Effect |
|---|---|
| `present-hz.txt` | frame-rate tier (content `30` / `40` / `60`) |
| `slot-page-shift.txt` | bitmap pool page granularity |
| `render-slots.txt` | render slots (1..4) |
| `profile-detail` | sub-timings (when off every sub-timing reads 0.000, which is misleading) |
| `pool-range-stats` | pool range statistics |
| `no-dirty-uploads` | disable dirty-range incremental uploads (for comparison) |
| `touch-trace` / `click-trace` | touch and click diagnostics |

## 9. Not done / still open

- **Mali still reports `GROUP_ERROR_FATAL` on the character-creation screen** (section 3), root
  cause not located. Suspects: the upload copies are not chunked by work done
  (`sub_chunk_flush()` counts draws only), so the whole burst may land in one oversized command
  buffer; and the pool / staging peak during the upload.
- **Above ~50 fps on Mali needs draw-call batching**, and D2R's ordering constraints are strict, so
  this is high risk and deferred.
- **BC textures are always decoded on the CPU**; `DM_BC_NATIVE` is off by default (it corrupts the
  picture).
- The overlay control scale (`0.62` floor) is an empirical value; no systematic accessibility
  testing was done.
